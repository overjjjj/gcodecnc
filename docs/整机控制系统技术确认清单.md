## 2. 已确认的总体方案

以下内容已作为当前开发基线：

1. 整体采用“PC 软件 + 自研 CQ8 驱控一体系统 + 机床本体”的控制方案，CQ8 的功能、协议和数据结构由本项目自主定义。
2. PC 负责模型、工艺、刀路、仿真、G 代码、安全校验、任务管理和 G 代码下发。
3. CQ8 负责 G 代码接收与解释、轨迹规划、实时插补、轴控制、PLC、机床 IO 和实时安全联锁。
4. Windows PC 不直接承担毫秒级插补和伺服闭环控制。
5. PC 必须支持完整程序下载和持续流式下发两种能力。
6. 产品层暂以 10000 行作为大程序流式下发的初始切换条件之一，但底层不能只按行数判断，还必须考虑程序字节数、CQ8 可用存储空间、短线段密度和预计执行时间。
7. 大程序通过 PC 持续向 CQ8 的 G 代码接收环形缓冲区发送数据。
8. CQ8 内部应分别设置“未解析 G 代码接收缓冲区”和“已规划轨迹缓冲区”，两者不能混用。
9. 工艺方案、刀具和加工参数由人员选择或确认，系统可以识别和推荐，但不能完全自动决定。
10. CQ8 当前不急于实际部署，CAM 和 PC 控制软件先完成接口、任务模型和状态机预留。
11. PC 与 CQ8 通过有线以太网口通信，第一阶段采用 TCP 长连接承载 G 代码流、控制命令和状态回传；CQ8 作为 TCP 服务端，PC 作为客户端主动连接；IP 地址、端口和应用层报文协议仍需专项确认。
12. 第一阶段只建立一个 TCP 长连接，控制、状态、报警和 G 代码程序消息通过应用层消息类型复用；单连接内部必须实施消息优先级，避免大程序传输阻塞关键状态和控制响应。
13. PC 端采用 `CNEXT-CAM` 与 `CNC_SYSTEM` 双进程架构。`CNEXT-CAM` 负责离线 CAM，`CNC_SYSTEM` 是唯一允许连接 CQ8、下发程序和提交在线控制请求的 PC 进程。
14. `CNEXT-CAM` 与 `CNC_SYSTEM` 通过版本化 Job Package 文件交接加工任务，文件是唯一可信交接载体；本地 IPC 只负责通知，不传递最终可信加工内容；CAM 提交和控制系统接收均要求人工确认。
15. 手轮、点动和回零输入直接进入 CQ8，由 CQ8 完成模式判断、轴选择、倍率处理和运动控制，不经过 Windows 或 CNC_SYSTEM 转发。
16. CQ8 统一仲裁实体面板、内部状态机和 CNC_SYSTEM 的控制请求；实体面板的停止和进给保持优先于 PC 控制请求，PC 不能覆盖本地停止状态。
17. 急停、防护门安全联锁和伺服/主轴 STO 由独立硬件安全链完成；CQ8 接收安全状态并参与运行联锁和报警，但普通 CQ8 软件或 PC 软件均不得旁路安全链。
18. 首期整机按三轴加工中心交付，控制对象为 X、Y、Z 三个进给轴和一个主轴；第四轴、第五轴只预留接口、参数和数据结构，不包含四五轴联动、运动学、RTCP、碰撞及实机验收。
19. 首期整机包含自动刀库和自动换刀完整闭环；CQ8/PLC 必须完成 `T`/`M06` 执行、刀号一致性、动作联锁、到位检测、超时报警及换刀中断恢复。
20. 核心用户是同时承担机床操作和工艺设计编程的现场操作员；界面按“设计-验证-提交-装机-执行-追溯”任务阶段组织，不按操作员和工艺工程师两个岗位割裂。
21. 界面功能结构参考《加工中心控制系统用户使用手册 manual_zh_CN(1)》，但保持 CNEXT-CAM/CNC_SYSTEM 双进程、CQ8 控制边界、人工工艺确认、Job Package 和流式下发等自有架构。
22. 机床自动加工期间允许操作员使用 CNEXT-CAM 设计下一任务；当前运行任务保持不可变，CAM 仅接收只读机床状态，新任务只能进入 CNC_SYSTEM 待接收队列，不得自动下载或替换当前任务。
23. 只有急停、安全链、伺服、主轴和刀库等高等级报警强制将 CNC_SYSTEM 切到前台；普通报警在 CAM 中持续提示，一般警告不打断设计；界面抢占不得自动触发复位或恢复动作。
24. 首期暂不固定生产屏幕尺寸和分辨率；CNC_SYSTEM 与 CNEXT-CAM 不得依赖固定窗口坐标，应采用可缩放布局，并在硬件选型后冻结目标分辨率和触摸面板规格。
25. 机床辅助功能暂不冻结，待现场确认实际硬件后再确定；当前只预留 Machine Profile、可配置 IO、PLC 状态机、报警和界面扩展能力，不为外冷、内冷、润滑、排屑、夹具、测头、自动门或上下料预设具体动作。
26. 软件保持机床无关的通用核心，现场通过版本化“机床配置包”适配具体设备；配置包是轴、主轴、刀库、IO、联锁、报警、Machine Profile 和 PLC 配置的唯一受控交付载体。
27. CQ8 使用自主定义并版本化的 G 代码方言，语法兼容常见 ISO/Fanuc 使用习惯；CNEXT-CAM 以 CQ8 为主后处理目标，Siemens/Fanuc 仅保留可选兼容和回归用途。
28. 首期全链路只支持毫米单位 `G21`；CNEXT-CAM 不生成 `G20`，CNC_SYSTEM 与 CQ8 对英制程序明确拒绝，不进行隐式单位换算。
29. CQ8 首期接受 I/J/K 和 R 两种圆弧输入，CNEXT-CAM 统一生成 I/J/K；整圆只允许 I/J/K，R 正负分别表示小圆弧/大圆弧，几何超过容差时拒绝执行。
30. CQ8 程序号、N 行号、注释和 `%` 等外层程序格式暂不冻结，等待用户后续提供规则或样例程序；流式通信的绝对递增序号不依赖这些文本格式。
31. 首期部署为“一台 PC + 一套 CQ8 驱控一体系统”：同一台 PC 运行 CNEXT-CAM 和 CNC_SYSTEM 两个独立进程，通过本地 Job Package/IPC 协同，CNC_SYSTEM 经有线以太网连接 CQ8；RK3568 不进入首期生产基线。
32. 首期正式生产软件平台为 Windows x64；CNEXT-CAM、CNC_SYSTEM、Qt、OpenCascade 和其他运行依赖统一使用 64 位生产工具链，现有 CNC_SYSTEM 32 位 MinGW 版本只保留为临时调试基线。

### 5.2.1 PC 端软件部署边界（已确认）

当前已有两个独立软件工程：

- `CNEXT-CAM`：模型、特征、Setup、工艺、刀具、刀路、仿真、G 代码生成和离线安全校验；
- `CNC_SYSTEM`：机床操作界面、程序管理、面板按键、坐标、刀具、诊断、报警及在线控制。

已确认保持两个独立进程，通过受控任务交接协同：

1. CNEXT-CAM 生成并冻结包含程序哈希、安全校验结果、刀具、坐标和追溯信息的 Job Package；
2. CNC_SYSTEM 导入并复核 Job Package，作为 PC 端唯一持有 CQ8 TCP 连接和机床控制权的进程；
3. CNEXT-CAM 不直接发送循环启动、进给保持、复位或其他机床动作命令；
4. CNC_SYSTEM 负责完整下载、流式下发、缓冲监控、机床状态、报警和运行恢复；
5. 两个软件可统一视觉和导航体验，但崩溃、升级和权限边界相互隔离；
6. 同一任务的模型版本、程序哈希和加工状态在两个进程间保持可追溯映射。

控制权约束：

- `CNEXT-CAM` 不建立 CQ8 控制连接；
- `CNC_SYSTEM` 是 PC 端唯一 CQ8 控制主体；
- 同一时刻只允许一个有效控制会话；
- 两个进程之间的人工确认流程已冻结，任务包具体容器和字段 Schema 仍需细化。

### 5.2.2 Job Package 任务交接（已确认）

交接流程：

1. `CNEXT-CAM` 完成模型、工艺、刀路、G 代码和安全校验；
2. 用户在 `CNEXT-CAM` 中明确执行“提交到控制系统”；
3. `CNEXT-CAM` 生成不可被静默覆盖的版本化 Job Package；
4. 本地 IPC 可以通知 `CNC_SYSTEM` 有新任务，但不能代替任务包文件；
5. `CNC_SYSTEM` 校验格式版本、内容哈希、程序哈希和安全结果；
6. `CNC_SYSTEM` 展示工件、Setup、坐标系、刀具、程序和风险摘要；
7. 操作人员人工确认后，才允许进入 CQ8 下载或流式下发阶段；
8. 任务包内容发生任何改变时生成新版本，旧确认自动失效。

Job Package 至少包含：

- 包格式版本、任务 ID、创建时间和创建软件版本；
- STEP 来源指纹、最终验收模型标识和项目版本；
- 已确认 Setup、加工方向、G54 和毛坯信息；
- 已确认加工特征和加工操作；
- 刀具、刀柄、补偿号和最终工艺参数；
- 控制器目标和最终 G 代码；
- 程序行数、字节数、程序哈希和预计下发模式；
- 安全校验规则版本、结果和不可绕过的阻断项；
- 仿真摘要和操作追溯映射；
- 包内容清单及整体哈希。

待细化：包容器格式、字段 Schema、签名方式、存储目录、保留周期和旧版本迁移。

### 5.2.3 整机控制权分配（部分已确认）

| 控制事项 | 建议控制主体 | PC/CNC_SYSTEM 的作用 | 当前状态 |
|---|---|---|---|
| 急停 | 独立双通道硬件安全链 | 只显示状态和记录事件 | 架构已确认，具体电气待设计 |
| 防护门和安全门锁 | 安全硬件与 CQ8 联锁 | 显示状态，不允许软件绕过 | 架构已确认，具体电气待设计 |
| 伺服和主轴 STO | 独立安全硬件直接控制 | 只显示状态 | 架构已确认，具体电气待设计 |
| 正负硬限位 | 硬件信号直接进入 CQ8/安全链 | 显示报警 | 原则认可，待电气确认 |
| 循环启动 | 实体面板输入 CQ8；PC 可提交请求 | 显示启动条件和请求结果 | 待最终确认 |
| 进给保持和受控停止 | 实体面板输入 CQ8；PC 可提交请求 | 显示保持原因和恢复条件 | 待最终确认 |
| 复位 | 实体面板输入 CQ8；PC 只能请求允许软件复位的故障 | 显示不可复位原因 | 待最终确认 |
| 手轮、点动和回零 | 输入直接进入 CQ8，不通过 Windows 转发 | 显示模式、轴选择、倍率和位置 | 已确认 |
| 程序下载和流式下发 | CNC_SYSTEM 经 TCP 向 CQ8 提交 | 主责 | 已确认 |
| CAM 操作 | CNEXT-CAM | 无任何机床运动控制权限 | 已确认 |

已确认 CQ8 控制仲裁优先级：

1. 独立硬件安全链和急停；
2. 实体面板停止和进给保持；
3. CQ8 内部限位、报警及状态机；
4. 实体面板启动、点动、手轮和回零；
5. CNC_SYSTEM 通过 TCP 提交的控制请求；
6. 普通状态查询和程序传输。

CQ8 对所有启动和运动请求进行最终条件判断。任何 PC 请求均不能覆盖急停、安全联锁、本地保持、限位或 CQ8 报警状态。

控制原则：

- 所有 PC 控制命令都是请求，CQ8 根据当前模式、权限、安全链和机床状态决定接受或拒绝；
- PC 崩溃、Windows 卡顿或网络断开时，安全链、实体面板输入和 CQ8 本地控制仍应工作；
- 急停不得设计为普通 TCP 命令；
- 安全状态和硬件联锁不得提供普通用户可绕过的软件开关；
- 最终方案必须与操作面板、IO 点表、电气原理图和 CQ8 状态机共同冻结。

- 一个主轴；

- 第四轴和第五轴仅做扩展预留；
- 首期不实现或验收四五轴后处理、旋转轴插补、运动学变换、RTCP 和多轴碰撞检查。

## 6. G 代码和流式下发技术确认

### 6.0 以太网通信基线

已确认 PC 与自研 CQ8 通过有线以太网口通信，第一阶段统一采用 TCP 长连接。以下应用层项目仍需由 PC 软件团队和 CQ8 团队共同定义：

- 已确认 CQ8 作为 TCP 服务端、PC 主动建立连接；
- 默认 IP、子网掩码、网关和端口；
- 是否采用独立控制网段和双网口隔离；
- 连接、认证、心跳、超时和重连状态机；
- 字节序、字符编码、报文头和最大报文长度；
- 报文序号、CRC、确认、超时和重发机制；
- 已确认 G 代码、控制命令和状态通过单个 TCP 长连接复用；
- 通信周期、允许抖动、最大带宽和最坏延迟；
- 协议版本协商以及不兼容版本的拒绝策略；
- 抓包、诊断、日志和协议仿真工具。

TCP 长连接承载任务下发、G 代码流、控制命令和可靠状态。高频非关键遥测只有在性能测试证明 TCP 不满足需求时，再评审是否增加独立 UDP 通道。CQ8 的实时插补不得依赖以太网报文的确定性。

已确认第一阶段使用单个 TCP 长连接进行应用层消息复用，不拆分独立程序连接。实现必须限制单个 G 代码分块大小，并优先调度报警、控制响应、心跳和缓冲临界状态。

### 6.1 下发模式

| 模式 | 适用条件 | 启动规则 |
|---|---|---|
| 整包下载 | 程序能够完整存入 CQ8，且未超过配置阈值 | 完整接收并校验后启动 |
| 预下载流式执行 | 大程序、复杂程序或存储不足 | 先达到接收和轨迹安全水位，再允许启动 |
| 仅下载不执行 | 调试、审查和程序预装载 | 下载后保持待确认状态 |

确认原则：

1. 10000 行是初始产品策略，不是唯一的底层安全阈值。
2. 最终模式由程序行数、总字节数、CQ8 可用内存和程序复杂度共同决定。
3. 用户界面应显示当前下发模式、总量、已发送、已确认、已执行和缓冲水位。
4. PC 只能发送已经完成安全校验且哈希固定的程序版本。
5. 加工过程中修改 G 代码必须产生新版本并重新校验，不能继续原任务。

### 6.2 两级缓冲区

| 缓冲区 | 保存内容 | 主要责任 |
|---|---|---|
| G 代码接收环形缓冲区 | PC 已发送、CQ8 尚未解析的程序块 | 吸收通信抖动和限制 PC 发送速率 |
| 轨迹规划缓冲区 | CQ8 已解释和完成速度规划、等待实时插补的轨迹 | 保证实时运动连续和可控减速 |

待 CQ8 团队确认：

- 两个缓冲区可用内存容量；
- 最大程序块长度；
- 正常、高、低和临界水位；
- 轨迹缓冲能够覆盖的最低加工时间；
- 环形指针回绕和并发访问机制；
- 缓冲区状态回传周期；
- 解析速度和最坏短线段处理能力。

建议轨迹规划缓冲按“可执行时间”定义，启动前至少储备 10～30 秒轨迹；最终值通过 CQ8 性能测试确定。

### 6.3 传输协议字段

PC 发送的数据包建议包含：

- 协议版本；
- 任务 ID；
- 程序版本和整体哈希；
- 程序总字节数和总程序块数；
- 分块序号和起始程序块号；
- 有效数据长度和 G 代码内容；
- 分块 CRC；
- 首块、末块和控制标志。

CQ8 应回传：

- 当前任务 ID 和程序哈希；
- 已接收、已解析和已执行序号；
- 接收缓冲区剩余容量；
- 轨迹缓冲区剩余时间或轨迹段数；
- CRC 结果和指定分块重发请求；
- 运行、保持、停止、完成和报警状态。

序号必须绝对递增，不能只使用环形缓冲物理地址，避免指针回绕后重复执行旧数据。

### 6.4 流式启动条件

下列条件全部满足后才能允许循环启动：

- PC 侧完整程序已完成安全检查；
- 程序版本和整体哈希已冻结；
- CQ8 已确认任务 ID、协议版本和程序版本；
- 程序头、安全起始段、坐标系和初始刀具信息完整；
- G 代码接收缓冲区达到启动水位；
- 轨迹规划缓冲区达到最低可执行时间；
- 刀具表、工件坐标系和 Machine Profile 版本一致；
- CQ8、伺服、主轴、PLC 和安全链状态允许启动；
- 操作员在机床侧完成最终启动确认。

### 6.5 通信中断策略

| 场景 | 推荐处理 |
|---|---|
| 短暂通信抖动且缓冲充足 | CQ8 继续执行，PC 自动重连和补发 |
| 接收缓冲进入低水位 | 提高发送优先级并产生预警 |
| 轨迹缓冲接近临界水位 | CQ8 提前规划受控减速并进入进给保持 |
| 长时间断线 | 保持停止，禁止自动恢复运动 |
| PC 崩溃或重启 | 从 CQ8 查询任务、哈希和执行位置，禁止默认从头执行 |
| 任务或程序哈希不一致 | 拒绝续传和恢复，要求重新校验并建立新任务 |

普通通信中断不建议直接触发急停；应由 CQ8 进行受控减速。数据损坏、安全状态异常或硬件安全链触发时，按对应安全等级停止。

### 6.6 程序暂停和恢复

恢复信息至少包括：

- 任务 ID、程序版本和哈希；
- 已接收、已解析和已执行位置；
- 当前刀具、刀补和磨损补偿；
- G54 等工件坐标系；
- 主轴、冷却和模态 G/M 状态；
- 固定循环状态和子程序调用栈；
- 当前机械坐标和工件坐标；
- 暂停原因和恢复允许条件。

不能简单地从任意当前行恢复。CQ8 应生成安全恢复点；圆弧、固定循环、刀补建立、换刀和宏循环中间位置不得由 PC 强制续行。

### 6.7 函数化 G 代码

1. 重复孔加工、重复槽型和重复轮廓优先使用固定循环或子程序，避免程序冗余。
2. G80、安全起始代码、程序头尾和控制器专用代码由受控模板配置。
3. 刀具更换、主轴、冷却、坐标系和关键安全状态保留在主程序中。
4. PC 执行预览必须能够展开固定循环、子程序、参数调用和模态状态。
5. CQ8 回传执行程序块时，PC 应能映射到原加工操作、模型特征和展开轨迹。
6. 甲方需确认 CQ8 支持的固定循环、子程序、宏变量、嵌套层数和参数传递规则。
