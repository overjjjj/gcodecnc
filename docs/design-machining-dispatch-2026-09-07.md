# 设计加工实现下发与评审

## 协作方式

主线程负责范围、验收标准、实现评审和返修下发，不编辑生产实现。
实现子线程使用 GPT-5.6-sol / medium，负责测试、生产实现、工程注册和验证。
本次实现子线程：`/root/design_d1a_implementation`；已下发 D1-A，等待实现与评审。
当前工作区包含已通过验证但未提交的基线整理，必须保留；不得 reset、整分支合并、提交或推送。

## D1 分批

先完成 D1-A 批量确认事务抽取，再评审 D1-B 工序状态唯一来源。
两批不同时改 MainWindow、OperationListPanel 和 ProjectManager，避免状态迁移与确认迁移混在一个补丁中。

### D1-A：本次下发

目标：两处 MainWindow 批量正式工序确认使用同一个无 UI 的设计加工服务。

- 服务复用现有 OperationFactory，不创建第二套工序类型或确认规则。
- 输入是本次明确人工确认的候选集合、确认意图及当前来源/Setup/WCS 上下文。
- 整批确认成功才返回完整工序集合；任何一项失败不返回可提交的部分工序，调用方不写项目或工序列表。
- 不自动确认；不改变现有策略预检、几何限制、刀具限制或刀路校验；校验失败不标为有效。
- 保留两条界面路径的阶段赋值、顺序、选中行为和错误提示语义。
- MainWindow 仍负责现有交互及最终一次提交；本批不宣称已完成 UI/项目唯一状态源。
- 服务放在 process_design/operations 或适合的应用服务目录；不得引入 QWidget、MainWindow、通信、后处理或策略实现依赖。
- 不调整刀路算法、冷却、文件格式、输出门禁，不迁入其他分支工艺能力。

验收：

1. 先有失败测试证据，再实现。真实 OperationFactory 行为测试可在无 MainWindow 环境运行。
2. 覆盖全部成功且保持顺序、缺失人工确认、后项失败且无部分结果、空批次和原有上下文拒绝。
3. 两个真实 UI 调用点都接入服务；不得新增从未使用的包装类。
4. 用行为测试验证整批失败不提交；源码接线检查只能作为补充。
5. qmake 与测试脚本注册完整；架构门禁、相关确认/生命周期测试、Debug 构建和全量回归通过。
6. 交付改动清单、RED/GREEN 证据、测试日志、未覆盖边界。主线程审核前不进入 D1-B。

### D1-B：待 D1-A 评审后下发

项目成为正式工序唯一状态源，面板展示并提交编辑命令；覆盖启停、排序、删除、换刀、重算与保存重开。
先核对现有撤销支持范围，不因架构重构新增未经设计的全局撤销系统。
验收要求项目变化正确刷新面板，UI 命令只产生一次状态变更，没有同步回环和隐式覆盖。

## 评审重点

检查确认与刀路有效状态的先后顺序、失败分支零提交、上下文完整传递、两条入口一致性、
测试是否执行真实生产逻辑，以及是否保留本轮开始前已有的基线改动。
已有快照/输出门禁问题仍按基线文档记录，本批不得借结构改造声称这些问题已修复。
